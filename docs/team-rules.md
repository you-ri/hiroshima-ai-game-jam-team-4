# チーム運用ルール（複数人 × 複数 AI 環境）

前提: **メンバーごとにマシンも AI エージェントも違い、同時に別の機能を書いている。**
壊れるのはたいてい実装ではなく、同じファイルを二人が触ったときと、片方の手元でしか通らない設定。

## 1. 担当をフォルダで分ける

- 1 機能 = `actors/<機能>/` フォルダ 1 つ = 担当者 1 人。
- 自分のフォルダの中は自由。**他人のフォルダは読むだけ。** 直したいことがあれば本人に言う。
- `scenes/main.tscn` は各 actor をインスタンス化するだけの薄いシーンに保つ。
  ここが厚くなるほど全員のコンフリクトが増える。

## 2. `.tscn` は同時編集しない

`.tscn` はテキストだが**行マージが破綻しやすい**（`load_steps`、`ExtResource` の id、ノード順が絡む）。

- 同じ `.tscn` を二人が同時に触らない。触る前に宣言する。
- コンフリクトしたら、**手でマージせず片方を捨てて作り直す方が速い**ことが多い。
- 特に `project.godot` の `[input]` セクションは全員が触りたくなる。**追加は 1 人にまとめるか、行を離して足す。**

## 3. ブランチとコミット

```sh
git switch -c feat/player-move
# 作業 → import / check / verify
git add <触ったファイルだけ>
git commit -m "プレイヤーの左右移動を追加"
git push -u origin feat/player-move
```

- `main` へ直接 push しない。PR を作る。
- ジャム中は**小さく頻繁に**。半日分を 1 コミットにしない。
- `git add .` を避ける。`.godot/` は無視されるが、検証スクリプトの残骸や個人設定が混ざる。
- コミットメッセージは日本語でよい。何を作ったかが分かれば形式は問わない。

### コミットしてはいけないもの

| 対象 | 理由 |
|---|---|
| `.godot/` | 生成物（gitignore 済み） |
| `.godot-path` | 個人のマシン固有パス（gitignore 済み） |
| `_verify_*.gd` / `.gd.uid` | 使い捨ての検証スクリプト（gitignore 済み。使ったら消す） |
| Godot バイナリのフルパスを書いたスクリプト | 他人の環境で動かない。`tools/godot.sh` を使う |

## 4. 環境差を持ち込まない

- **OS は Windows、シェルは Git Bash で揃える。** 別 OS 向けの分岐をコードやドキュメントに足さない。
- Godot は **4.7.1-stable で揃える。** バージョン差は `.tscn` の書式差分になり、無意味なコンフリクトを生む。
- パスは必ず `tools/godot.sh` 経由。「自分の環境ではこのパス」をコードやドキュメントに書かない。
- 改行は LF、文字コードは UTF-8（[.gitattributes](../.gitattributes) / [.editorconfig](../.editorconfig)）。
- 「自分の手元では動く」は報告として不十分。**`check` / `verify` の出力を貼る。**

## 5. AI エージェントへの共有

メンバーの AI は互いの会話を見られない。**共有される文脈はリポジトリの中身だけ。**

- ルールを変えたら [AGENTS.md](../AGENTS.md) を直す（`CLAUDE.md` はこれを読み込むだけなので追従不要）。
- 構成・仕様・命名の判断をしたら [decisions.md](decisions.md) に 1 行足す。
  「なぜそうしたか」が無いと、次のメンバーの AI が善意で元に戻す。
- 個人環境のスキルやプロンプトで得た知見は、`docs/` に書き戻して初めてチームの資産になる。
- 大きめの実装を AI に投げる前に、**触るファイルを先に宣言させる**。着手後では衝突を防げない。

## 6. 詰まったとき

1. [troubleshooting.md](troubleshooting.md) の症状表を引く
2. `.godot/` を消して `bash tools/godot.sh import` からやり直す
3. それでもだめならチームに投げる。ジャムでは 30 分悩むより聞いた方が速い
